# 进化模式参考库

> 收录各类AI Agent自循环迭代的最佳实践模式

## 模式目录

### 1. 定时扫描型 (Scheduled Scanning)

**适用场景**：
- 知识密集型Skill（研究、学习类）
- 领域快速变化（AI技术、市场趋势）
- 需要持续跟踪外部进展

**核心机制**：
```
Cron定时触发 → 多源搜索 → 差异分析 → 知识更新
```

**成功案例**：
- deep-dive skill：每3天扫描同类研究工具
- news-tracker：每日扫描行业新闻

**配置模板**：
```yaml
triggers:
  cron:
    enabled: true
    interval: "0 0 */3 * *"  # 每3天

perception:
  search_keywords:
    - "[domain] best practice"
    - "[domain] new method"
  sources:
    - arxiv
    - github
    - tech_blogs
```

### 2. 反馈驱动型 (Feedback-Driven)

**适用场景**：
- 交互密集型Agent（客服、助手）
- 需要持续优化用户体验
- 用户反馈容易获取

**核心机制**：
```
用户交互 → 收集反馈 → 失败分析 → Prompt优化
```

**成功案例**：
- Claude的RLHF训练
- 客服Agent的回复优化

**配置模板**：
```yaml
triggers:
  feedback:
    enabled: true
    threshold: 3  # 连续3次负面反馈触发
  performance:
    enabled: true
    metric: "success_rate"
    threshold: 0.85

perception:
  feedback_channels:
    - explicit_rating  # 显式评分
    - implicit_signal  # 隐式信号（重试、放弃等）
```

---

### 3. 竞争进化型 (Competitive Evolution)

**适用场景**：
- 需要多方案对比（Prompt、工作流）
- 有明确的性能指标
- 可以A/B测试

**核心机制**：
```
多版本并行 → A/B测试 → 优胜劣汰 → 变异生成新版本
```

**成功案例**：
- 广告系统创意优化
- 推荐算法参数调优

**配置模板**：
```yaml
triggers:
  competition:
    enabled: true
    population_size: 5  # 保持5个版本
    selection_rate: 0.2  # 淘汰20%
    mutation_rate: 0.3  # 变异30%

evaluation:
  criteria:
    - metric: "conversion_rate"
      weight: 0.5
    - metric: "user_satisfaction"
      weight: 0.3
    - metric: "efficiency"
      weight: 0.2
```

### 4. 性能触发型 (Performance-Triggered)

**适用场景**：
- SLA要求严格的生产系统
- 性能下降需要快速响应
- 自动故障恢复

**核心机制**：
```
持续监控 → 异常检测 → 自动诊断 → 修复/回滚
```

**配置模板**：
```yaml
triggers:
  monitoring:
    enabled: true
    metrics:
      - name: "success_rate"
        threshold: 0.95
        operator: "<"
      - name: "latency_p99"
        threshold: 2000
        operator: ">"
      - name: "error_rate"
        threshold: 0.05
        operator: ">"

execution:
  auto_remmediate: true  # 自动修复
  escalation: true  # 升级通知
```

### 模式31: 动态自进化评估环境 (Dynamic Self-Evolution Evaluation Environment)

**核心思想**: 将静态基准评测转化为动态RL风格的自进化评测环境，全面评估Agent在进化过程中的表现、退化、泛化和成本

**研究来源**: SEAGym (清华大学, 2026-06-16, arXiv:2606.17546)

**核心架构**:
```
┌─────────────────────────────────────────────────────────┐
│              SEAGym 动态自进化评估环境                    │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐   │
│  │              Agent Harness (被测系统)             │   │
│  │  • 策略函数 (任务执行)     • 更新规则 (Harness更新) │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │              环境接口 ( rollouts / update )       │   │
│  │  • 任务采样    • 反馈生成    • 快照记录            │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │              多视角评估视图                       │   │
│  │  ┌─────────┐ ┌─────────┐ ┌─────────┐            │   │
│  │  │Train Batch│ │Update Val│ │ID Transfer│         │   │
│  │  │(训练批次) │ │(更新验证)│ │(分布内迁移)│         │   │
│  │  └─────────┘ └─────────┘ └─────────┘            │   │
│  │  ┌─────────┐ ┌─────────┐ ┌─────────┐            │   │
│  │  │OOD Transfer│ │ Replay  │ │ Cost    │           │   │
│  │  │(分布外迁移)│ │(回测)   │ │(成本)   │           │   │
│  │  └─────────┘ └─────────┘ └─────────┘            │   │
│  └─────────────────────────────────────────────────┘   │
```

**关键创新**:
1. **Agent Harness形式化**: 将Agent系统建模为可更新的Harness（提示词、记忆、工具、中间件等）
2. **RL风格环境**: Agent同时提供任务策略和Harness更新规则，环境负责任务采样和评估
3. **多视角评估**: 不仅看最终分数，还看更新过程本身
4. **快照机制**: 记录每次更新后的Agent状态，支持回滚和对比

**评估视图详解**:
| 视图 | 用途 | 揭示问题 |
|------|------|----------|
| **Train Batch** | 训练批次表现 | 是否在学习 |
| **Update Validation** | 冻结验证集 | 是否过拟合 |
| **ID Transfer** | 同分布迁移 | 泛化能力 |
| **OOD Transfer** | 异分布迁移 | 鲁棒性 |
| **Replay** | 历史任务重测 | 灾难性遗忘 |
| **Cost** | Token/时间消耗 | 效率 |

**关键发现** (SEAGym实验):
- 频繁更新不一定提升held-out性能
- 有用的中间快照可能后续退化
- 源多样性和后端模型影响Harness可靠性
- 验证集增益不一定迁移

**适用场景**:
- 自进化Agent研发
- 进化算法比较
- 生产环境进化监控

**配置示例**:
```yaml
seagym_eval:
  schedule:
    type: "epoch_based"  # 或 "single_task", "online_transfer"
    epochs: 10
    batch_size: 50
    
  views:
    train_batch: true
    update_validation: true
    id_transfer: true
    ood_transfer: true
    replay: true
    cost_tracking: true
    
  snapshot:
    frequency: "every_update"
    retention: "all"  # 或 "best_k"
    
  benchmarks:
    - name: "Terminal-Bench-2.0"
      type: "code"
    - name: "HLE"
      type: "reasoning"
```

**与现有模式的关系**:
- 现有模式关注"如何进化"，本模式关注"如何评估进化"
- 可与任何自进化模式组合使用
- 特别推荐与模式16 (能力保持型进化) 组合，监控遗忘

## 进化评估框架

### 评估维度

| 维度 | 指标 | 权重 | 评估方法 |
|------|------|------|----------|
| **效果** | 成功率 | 40% | 任务完成统计 |
| **效率** | Token/时间消耗 | 25% | 性能监控 |
| **体验** | 用户满意度 | 25% | 反馈收集 |
| **稳定** | 失败率/异常 | 10% | 错误日志 |

### 进化质量评级

- **S级**：所有指标提升 > 20%，无副作用
- **A级**：核心指标提升 > 10%，无重大副作用
- **B级**：有提升但 < 10%，或有轻微副作用
- **C级**：无明显提升，或有明显副作用 → 回滚

## 常见陷阱与对策

### 陷阱1：过度进化
**症状**：频繁变更导致不稳定
**对策**：
- 设置冷却期（一次进化后至少N天才能下次）
- 建立变更队列，批量处理

### 陷阱2：局部最优
**症状**：在小范围内优化，错过更大改进机会
**对策**：
- 定期进行"探索性"大版本尝试
- 引入随机变异机制

### 陷阱3：用户困惑
**症状**：Agent行为频繁变化，用户难以适应
**对策**：：
- 核心行为保持稳定
- 重大变更提前告知
- 提供版本切换选项

### 陷阱4：进化停滞
**症状**：长期无有效改进
**对策**：
- 引入外部视角（其他Agent评估）
- 定期人工review

## 模式7：对抗训练进化 (Adversarial Training Evolution)

**核心思想**：通过内部竞争机制推动能力边界扩展，无需外部数据即可实现自我增强

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│                  对抗训练进化系统                          │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────┐      生成难题      ┌──────────────┐  │
│  │  课程智能体    │ ────────────────→ │  执行智能体   │  │
│  │  (出题者)     │ ←──────────────── │  (解题者)    │  │
│  └──────────────┘      解题反馈      └──────────────┘  │
│         ↑                                    │         │
│         │         螺旋上升闭环                │         │
│         └────────────────────────────────────┘         │
└─────────────────────────────────────────────────────────┘
```

**适用场景**:
- 需要持续提升任务难度的场景
- 缺乏足够训练数据的领域
- 希望突破现有能力边界的探索性任务
- 数学推理、代码生成等可验证领域

**触发条件**:
- 执行智能体成功率超过阈值
- 课程智能体生成的新任务被成功解决
- 需要引入"不确定性奖励"和"重复惩罚"机制

**配置示例**:
```json
{
  "adversarial_training": {
    "curriculum_agent": {
      "reward_components": {
        "uncertainty_reward": "maximize when solver success rate ~50%",
        "tool_usage_reward": "incentive for tool-assisted solutions",
        "repetition_penalty": "BLEU-based similarity penalty"
      }
    },
    "solver_agent": {
      "multi_round_interaction": true,
      "tools": ["code_interpreter", "search", "calculator"],
      "self_consistency_voting": 10
    },
    "evolution_parameters": {
      "filter_threshold": "25%-75% success rate",
      "adaptive_learning_rate": true,
      "max_iterations": 100
    }
  }
}
```

**工业案例**: Agent 0 (2026)、R-Zero (2025) 在数学推理任务上实现18-24%能力提升

**注意事项**:
- 需要可验证的奖励信号（成功/失败）
- 伪标签准确率可能随迭代衰减，需要监控
- 不适合主观评估任务（如创意写作）

## 模式8：经验蒸馏自进化 (Experience Distillation Evolution)

**核心思想**：将原始执行轨迹提炼为可复用的战略原则，而非简单记忆案例

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│                  经验蒸馏自进化系统                        │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────┐    ┌──────────────┐    ┌──────────┐  │
│  │  在线交互层   │ → │  经验蒸馏层   │ → │ 策略进化层 │  │
│  │  (积累轨迹)   │    │ (提取原则)   │    │ (强化学习) │  │
│  └──────────────┘    └──────────────┘    └──────────┘  │
│         ↑                                      │       │
│         └────────────── 闭环反馈 ←─────────────┘       │
└─────────────────────────────────────────────────────────┘
```

**关键组件**:
1. **在线交互**：执行任务并积累完整轨迹
2. **离线蒸馏**：将轨迹抽象为可复用的战略原则
3. **语义去重**：避免重复原则的累积
4. **动态评分**：基于历史有效性持续评估原则质量
5. **策略强化**：使用提炼的原则作为上下文指导决策

**适用场景**:
- 需要长期记忆和知识积累的系统
- 复杂多跳问答任务
- 需要跨任务泛化能力的场景
- 持续性学习系统

**工业案例**: EvolveR (2025)、SkillOS (2026)

## 模式10：多智能体协同进化 (Multi-Agent Co-Evolution)

**核心思想**：多个专业智能体在共享持久内存中异步探索、反思和协作，实现开放式发现

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│              多智能体协同进化系统 (CORAL风格)              │
├─────────────────────────────────────────────────────────┤
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐    │
│  │ Agent A │  │ Agent B │  │ Agent C │  │ Agent D │    │
│  │ (探索者) │  │ (验证者) │  │ (综合者) │  │ (创新者) │    │
│  └────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘    │
│       └─────────────┴─────────────┴─────────────┘       │
│                         ↓                               │
│              ┌─────────────────────┐                    │
│              │   共享持久内存池     │                    │
│              │  • 发现的知识        │                    │
│              │  • 失败的教训        │                    │
│              │  • 成功的模式        │                    │
│              └─────────────────────┘                    │
│                         ↓                               │
│              ┌─────────────────────┐                    │
│              │  心跳干预机制        │                    │
│              │  (健康检查/资源管理)  │                    │
│              └─────────────────────┘                    │
└─────────────────────────────────────────────────────────┘
```

**关键机制**:
1. **异步执行**：各Agent独立运行，不阻塞彼此
2. **共享内存**：所有发现的知识实时同步到共享池
3. **心跳干预**：定期检查Agent健康状态，防止资源耗尽
4. **知识重用**：Agent可以查询并利用其他Agent的发现

**适用场景**:
- 开放式科学发现
- 复杂系统优化
- 需要多角度探索的创意任务
- 大规模搜索空间问题

**触发条件**:
- 单Agent长期无法突破
- 问题空间需要多样化探索策略
- 需要验证和交叉确认的发现

**配置示例**:
```yaml
co_evolution:
  agent_pool:
    - role: explorer
      strategy: random_walk
      count: 2
    - role: validator
      strategy: verification_first
      count: 1
    - role: synthesizer
      strategy: pattern_recognition
      count: 1
  shared_memory:
    type: persistent_vector_db
    sync_interval: 30s
  heartbeat:
    interval: 60s
    max_idle_time: 300s
    resource_limit:
      cpu: 80%
      memory: 4GB
```

**工业案例**: CORAL (2026) - 在Anthropic内核工程任务上将最佳成绩从1363提升到1103周期

**注意事项**:
- 需要仔细的并发控制
- 共享内存需要版本控制防止冲突
- 心跳机制防止"僵尸Agent"

## 模式11：元认知自我修改 (Metacognitive Self-Modification)

**核心思想**：不仅改进任务解决行为，还改进生成改进的机制本身 - 进化过程的进化

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│              元认知自我修改系统 (HyperAgents风格)          │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐   │
│  │              统一可编辑程序                        │   │
│  │  ┌─────────────────┐  ┌─────────────────────┐  │   │
│  │  │   Task Agent    │  │     Meta Agent      │  │   │
│  │  │  (解决目标任务)  │  │ (修改Task Agent和   │  │   │
│  │  │                 │  │   自身修改过程)     │  │   │
│  │  └─────────────────┘  └─────────────────────┘  │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │           Meta-Level Modification               │   │
```

### 模式22: 三层协同进化 (Three-Layer Co-Evolution, APEX)

**核心思想**: 同时进化三个正交维度——Harness修补、行为原则蒸馏、工作流拓扑进化

**研究来源**: APEX (Grace AI Technology, 2026-06, arXiv:2606.15363)

**三层架构**:
```
┌─────────────────────────────────────────────────────────┐
│              三层协同进化系统 (APEX风格)                   │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐   │

│  │  • 生成针对性规则补丁                            │   │
│  │  • 注入系统提示作为显式规则                       │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │  Layer 2: Principle Distillation (原则蒸馏)      │   │
│  │  • 从成功轨迹提取高质量行为模式                   │   │
│  │  • 蒸馏为可复用的行为原则                        │   │
│  │  • 在线应用于推理阶段                            │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │  Layer 3: Workflow Topology (拓扑进化)           │   │
│  │  • 基于结构健康度评估工作流DAG                   │   │
│  │  • 蒙特卡洛树搜索最优拓扑                        │   │
│  │  • 选择结构健康度最高的工作流                     │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │         APEX Health Score (综合健康评分)         │   │
│  │  H = f(覆盖率, 原则丰富度, 结构质量)              │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**关键创新**:
1. **正交进化轴**: 三个维度解决不同的失败模式，互不替代
2. **共享轨迹池**: 所有层从同一生产轨迹池提取证据
3. **复合健康评分**: APEX Health Score量化多维度进化进展
4. **无合成基准**: 完全基于真实生产轨迹，无需人工设计测试集

**APEX Health Score公式**:
```
H = w₁ × Coverage + w₂ × PrincipleRichness + w₃ × StructuralQuality

其中:
- Coverage: Harness补丁对失败模式的覆盖率
- PrincipleRichness: 蒸馏原则的数量和质量
- StructuralQuality: 工作流拓扑的结构健康度
```

**效果数据**:
- Joe Agent + 114真实任务轨迹 + 18天跨度 + 15节点计算集群
- APEX Health Score: 0.300 → 0.570 (+90%)
- 蒸馏6个新颖可复用原则
- 选出研究优先工作流拓扑 (结构评分0.900, +20%)
- 成本: 仅4 LLM调用 (~270s) 本地qwen2.5-coder:32b

**适用场景**: 
- 生产级Agent持续优化
- 需要多维度改进的复杂系统
- 真实部署环境（无合成基准）

**实施建议**:
```yaml

    l2_principles:
      quality_score_weights:
        lesson_length: 0.4
```

**核心思想**: 通过经验抽象和最小补丁修复，在资源受限环境下实现高效进化

**研究来源**: Polaris (2026, 改进的Gödel Agent框架 for Small Language Models)

**核心机制**:
```
┌─────────────────────────────────────────────────────────┐
│              经验抽象策略进化系统 (Polaris风格)            │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────┐    ┌──────────────┐    ┌──────────┐  │
│  │  经验抽象     │ → │  策略修复     │ → │ 最小补丁  │  │
│  │(识别通用模式)  │    │(定位问题根源) │    │(精准修改) │  │
│  └──────────────┘    └──────────────┘    └────┬─────┘  │
│                                               ↓       │
│  ┌─────────────────────────────────────────────────┐   │
│  │              小模型友好设计                        │   │
│  │  • 减少上下文长度需求                             │   │
│  │  • 降低推理复杂度                                 │   │
│  │  • 7B模型也能有效进化                             │   │
│  └─────────────────────────────────────────────────┘   │
```

**关键创新**:
1. **经验抽象**: 从具体失败中提取通用模式，而非记忆每个案例
2. **最小补丁**: 只修改必要代码，降低变更风险
3. **小模型适配**: 专为7B级别小模型优化

**效果**: 7B小模型在多项基准上超过现有大模型多智能体系统

**适用场景**: 
- 资源受限环境
- 边缘部署
- 成本敏感场景

### 模式25: 自我归因轨迹优化 (Self-Attributing Trajectory Optimization)

**核心思想**: 通过细粒度的因果归因，将稀疏的终局奖励转化为密集的过程监督信号

**研究来源**: AgentEvolver (阿里通义实验室, 2025-11)

**三模块架构**:
```
┌─────────────────────────────────────────────────────────┐
│              自我归因轨迹优化系统 (AgentEvolver风格)        │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────┐    ┌──────────────┐    ┌──────────┐  │
│  │ 自我提问      │ → │ 自我导航      │ → │ 自我归因  │  │
│  │(任务生成)     │    │(经验检索)     │    │(信用分配) │  │
│  └──────────────┘    └──────────────┘    └────┬─────┘  │
│                                               ↓       │
│  ┌─────────────────────────────────────────────────┐   │
│  │              闭环训练                            │   │
│  │  Master节点统一调度 + 服务化解耦 + 上下文管理器   │   │
│  └─────────────────────────────────────────────────┘   │
```

**三个核心机制**:

1. **自我提问 (Self-Questioning)**:
   - 利用LLM生成能力主动合成候选任务
   - 打破冷启动困境
   - 自动生成多样化训练课程

2. **自我导航 (Self-Navigating)**:
   - 将历史成功/失败抽象为结构化文本经验
   - 检索相似过往经验指导当前决策
   - "举一反三"能力

3. **自我归因 (Self-Attributing)**:
   - 基于LLM的过程奖励模型
   - 对轨迹中每个动作步骤细粒度因果分析
   - 将结果奖励转化为过程监督信号

**效果数据** (14B模型):
- AppWorld/BFCL: 29.8% → 57.6% (近乎翻倍)
- 最佳尝试: 76.7%
- 训练步数减少: 55.6% (AppWorld), 66.7% (BFCL)
- 跨域泛化: AppWorld训练模型用于BFCL，性能衰减极小

**适用场景**: 
- 长程复杂任务
- 奖励稀疏环境
- 需要快速收敛的训练

### 模式16: 能力保持型进化 (Capability-Preserving Evolution, CPE)

**核心思想**: 在自我进化过程中防止"遗忘"——新能力提升不以牺牲已有能力为代价

**研究来源**: "Do Self-Evolving Agents Forget?" (2026-05)

**实现要点**:
- 建立能力基线测试套件（Capability Baseline Suite）
- 每次进化前运行回归测试（Regression Testing）
- 多目标优化：提升目标能力 + 保持已有能力
- 帕累托前沿求解（Pareto Frontier Optimization）

**关键指标**:
```
能力保持率 = 进化后旧任务通过率 / 进化前旧任务通过率
净能力增益 = Σ(新任务提升) - Σ(旧任务退化)
```

**适用场景**: 长期运行的生产级Agent、关键业务系统

---

### 模式17: Harness优化进化 (Harness-Optimizing Evolution)

**核心思想**: 固定LLM参数，通过优化运行框架（Harness）实现能力提升

**研究来源**: Self-Harness (上海AI Lab, 2026-06, arXiv:2606.09498)

**三阶段循环**:
1. **Weakness Mining（弱点挖掘）**: 从执行轨迹分析失败模式
2. **Harness Proposal（框架提案）**: 生成针对性的Harness改进方案
3. **Proposal Validation（提案验证）**: 回归测试确保无退化

**四类改进类型**:
- 系统提示词修改（System Prompt Modification）
- 工具包装器添加（Tool Wrapper Enhancement）
- 验证步骤注入（Verification Step Injection）
- 规划模板更新（Planning Template Update）

**关键发现**: 
- Harness-Updating（生成更新）vs Harness-Benefit（从更新受益）能力分离
- 弱模型也能生成高质量更新，中等能力模型受益最大（倒U型曲线）

**适用场景**: 无法/不愿微调模型的场景、多模型统一优化

### 模式18: 回顾性工具包优化 (Retrospective Harness Optimization, RHO)

**核心思想**: 无需外部标准答案，通过自我反思改进工具包

**研究来源**: 港城大×微软 (2026-06, arXiv:2606.05922)

**三步进化**:
1. **诊断（Diagnosis）**: 用DPP筛选核心学习案例（难度70% + 多样性30%）
2. **重试（Retry）**: 自我验证 + 自我一致性检查
3. **改造（Refinement）**: 生成三套方案，内部评分选出最优

**效果数据**:
- SWE-BenchPro: 59% → 78% (+19%)
- 优于依赖标准答案的meta-Harness方法（62%）

**适用场景**: 无标准测试集的真实部署环境

### 模式26: 共进化评估器模式 (Co-Evolving Evaluator Pattern)

**核心思想**: 打破静态评估假设，让Agent与其评估器协同进化，适应非平稳环境

**研究来源**: Red Queen Gödel Machine (2026-06-24, arXiv:2606.26294)

**问题背景**: 传统自改进Agent假设评估标准静止不变，但真实环境是动态的。当Agent改进后，原有评估标准可能不再适用。

**核心机制**:
```
┌─────────────────────────────────────────────────────────┐
│              共进化评估器系统 (RQGM风格)                  │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐   │
│  │              Epoch 1 (固定评估器)                 │   │
│  │  Task Agent → 被 Evaluator 1 评估 → 改进        │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓ 评估器进化边界                │
│  ┌─────────────────────────────────────────────────┐   │
│  │              Epoch 2 (新评估器)                   │   │
│  │  Task Agent → 被 Evaluator 2 评估 → 改进        │   │
│  │  (Evaluator 2 在 Epoch 1 数据上训练)              │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  │  受控效用进化 (Controlled Utility Evolution)      │   │
│  │  • 每个Epoch内评估器固定                           │   │
│  │  • Epoch边界可更新评估器                           │   │
│  │  • 新评估器必须统计优于旧评估器才能替换             │   │
└─────────────────────────────────────────────────────────┘
```

**三个关键创新**:
1. **受控效用进化**: 搜索分为多个Epoch，每个Epoch内评估器固定，边界处可更新
2. **选择性擦除**: 替换评估器时只丢弃依赖旧评估器的记录，保留其他证据
3. **对抗正则化**: 可引入对抗目标（如对AI和人类作品同等严格）

**效果数据**:
- Polyglot代码任务: 71.7% vs 69.9% (SOTA)，节省1.35x-1.72x Token
- 论文写作: 接受率从21.8% → 40.5% (+1.86x)
- 证明评分: 准确率提升9%，搜索成本降低3x

**适用场景**:
- 无直接基准的任务（论文写作、证明评分）
- 评估缓慢或弱信息的任务
- 防止奖励黑客和基准饱和

**安全考量**:
- 评估器必须与任务Agent共同进化，而非独立漂移
- 需要ground truth数据集验证新评估器
- 收敛保证弱于静态评估，需要谨慎监控

### 模式27: 协议驱动自进化模式 (Protocol-Driven Self-Evolution)

**核心思想**: 通过标准化协议解耦"进化什么"与"如何进化"，实现可组合、可审计、可回滚的自进化

**研究来源**: Autogenesis Protocol (2026-05-07, arXiv:2604.15034)

**两层协议架构**:
```
┌─────────────────────────────────────────────────────────┐
│              协议驱动自进化系统 (AGP风格)                 │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐   │
│  │  Layer 1: RSPL (Resource Substrate Protocol)     │   │
│  │  资源基板协议层 - 定义进化的"什么"                 │   │
│  │  • Prompt (提示词)                               │   │
│  │  • Agent (智能体)                                │   │
│  │  • Tool/MCP/Skill (工具)                         │   │
│  │  • Environment (环境)                            │   │
│  │  • Memory (记忆)                                 │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │  Layer 2: SEPL (Self-Evolution Protocol)         │   │
│  │  自进化协议层 - 定义进化的"如何"                   │   │
│  │  • Reflect (反思)                                │   │
│  │  • Propose (提案)                                │   │
│  │  • Verify (验证)                                 │   │
│  │  • Commit (提交)                                 │   │
│  │  • Rollback (回滚)                               │   │
│  └─────────────────────────────────────────────────┘   │
```

**RSPL关键特性**:
- **显式状态**: 每个资源有明确的状态定义
- **生命周期管理**: 创建→激活→更新→退役的完整生命周期
- **版本化接口**: 所有变更可追溯、可回滚

**SEPL原子操作**:
1. **Reflect**: 分析执行轨迹，识别改进机会
2. **Propose**: 生成候选改进方案
3. **Verify**: 沙箱验证候选方案
4. **Commit**: 提交通过验证的变更
5. **Rollback**: 失败时回滚到稳定版本

**工业实现**: Autogenesis System (AGS)
- 在GPQA/AIME/GAIA/HLE/LeetCode上持续超越强基线
- 支持动态实例化、检索、优化协议资源

**配置示例**:
```yaml
autogenesis:
  rspl:
    resources:
      - type: prompt
        versioning: semantic
        rollback_limit: 10
      - type: tool
        lifecycle: [draft, verified, deprecated]
        signature_required: true
      - type: memory
        retention_policy: "90d_or_1000entries"
  sepl:
    operators:
      reflect:
        trigger: [on_failure, on_completion, periodic]
        evidence_sources: [trajectory, feedback, benchmark]
      propose:
        mutation_types: [incremental, structural, compositional]
        max_proposals_per_cycle: 3
      verify:
        sandbox: isolated_container
        test_coverage: 0.8
        regression_suite: mandatory
      commit:
        require_approval: [meta_level_changes]
        auto_promote: [incremental_changes]
      rollback:
        trigger: [health_check_fail, user_override, performance_degradation]
```

**适用场景**:
- 需要严格治理的企业环境
- 多团队协作的Agent系统
- 安全关键型应用
- 需要合规审计的场景

**与其他模式的关系**:
- 可审计技能图 (模式12): 协议驱动提供实现基础
- Harness工程自进化 (模式9): RSPL涵盖Harness组件
- 元认知自我修改 (模式11): SEPL提供安全的元级修改框架

### 模式29: 门控语义质量-多样性Harness进化 (Gated Semantic QD Harness Evolution)

**核心思想**: 通过门控机制结合语义质量-多样性搜索，自动生成多样化的优质Harness变体

**研究来源**: "Self-Evolving Agent Harnesses via Gated Semantic Quality-Diversity" (清华, 2026-07-15, arXiv:2607.13683)

**核心机制**:
```
┌─────────────────────────────────────────────────────────┐
│         门控语义质量-多样性Harness进化系统                 │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────┐    ┌──────────────┐    ┌──────────┐  │
│  │ 门控机制      │ → │ 语义QD搜索    │ → │ Harness  │  │
│  │(过滤低质量候选)│    │(多样性+质量)  │    │ 变异生成  │  │
│  └──────────────┘    └──────────────┘    └────┬─────┘  │
│                                               ↓       │
│  ┌─────────────────────────────────────────────────┐   │
│  │              语义行为描述符 (SBD)                  │   │
│  │  • 将Harness行为编码为语义向量                     │   │
│  │  • 支持语义层面的多样性度量                        │   │
│  │  • 避免基因型层面的冗余                           │   │
│  └─────────────────────────────────────────────────┘   │
│                                               ↓       │
│  ┌─────────────────────────────────────────────────┐   │
│  │              新颖性搜索 (Novelty Search)          │   │
│  │  • 鼓励探索行为空间的新区域                        │   │
│  │  • 防止早熟收敛                                  │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**技术细节**:
1. **门控机制 (Gating Mechanism)**: 使用轻量级LLM作为门控，过滤低质量Harness候选，减少昂贵评估成本
2. **语义行为描述符 (Semantic Behavioral Descriptor, SBD)**: 用自然语言描述Harness行为，支持语义相似度计算
3. **语义QD (Quality-Diversity)**: 在语义空间而非基因型空间维持多样性
4. **Edit-based变异**: 基于编辑操作生成Harness变体，而非从头生成

**效果数据**:
- 相比传统QD算法，评估次数减少40-60%
- 发现人类专家未考虑过的Harness配置

**适用场景**:

- 评估成本高的场景
- 需要探索性创新的场景

### 模式30: 自我意识递归自改进 (Self-Aware Recursive Self-Improvement, SARSI)

**核心思想**: 通过维护显式的自我模型，实现有监督的递归自改进，确保改进过程的安全性和可控性

**研究来源**: "Self-Aware Recursively Self-Improving Agents for Personal Singularity" (Chengshuai Yang, 2026-07-14, arXiv:2607.12254)

**核心架构**:
```
┌─────────────────────────────────────────────────────────┐
│           自我意识递归自改进系统 (SARSI)                  │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐   │
│  │              显式自我模型 Σ                       │   │
│  │  • I: 身份与血统 (Identity & Lineage)            │   │
│  │  • G: 目标层次结构 (Goal Hierarchy)              │   │
│  │  • S: 声明范围 (Declared Scope)                  │   │
│  │  • C: 能力与胜任度估计 (Capability Estimates)    │   │
│  │  • K: 认知边界 (Epistemic Boundaries)            │   │
│  │  • U: 不确定性 (Uncertainty)                     │   │
│  │  • R: 所有者与Agent关系 (Owner Relationships)    │   │
│  │  • D: 自传与发展历史 (Autobiographical History)  │   │
│  │  • P: 改进过程模型 (Improvement Process Model)   │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │              双层架构                             │   │
│  │  ┌─────────────┐      ┌─────────────────────┐   │   │
│  │  │  快任务循环  │      │  慢改进循环 (证据门控) │   │   │
│  │  │ Planner →   │      │ • 记忆/技能/策略更新   │   │   │
│  │  │ Executor →  │ ←──→ │ • 工具/适配器更新     │   │   │
│  │  │ Verifier    │      │ • 仅基于验证证据      │   │   │
│  │  └─────────────┘      └─────────────────────┘   │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │              外部治理平面                         │   │
│  │  • 权限强制执行    • 审计日志    • 关闭机制       │   │
│  └─────────────────────────────────────────────────┘   │
```

**关键创新**:
1. **功能自我感知**: 计算层面的自我建模（非现象意识），包含9个维度的显式表示
2. **范围路由器**: 将任务分配给可问责的主Agent，超出范围的通过结构化交接转移
3. **证据门控改进**: 只有基于验证证据的改进才能被接受
4. **外部治理平面**: 独立于Agent的控制层，确保关键权限不被篡改

**自改进层次**:
| 层次 | 修改组件 | 典型风险 | SARSI控制 |
|------|----------|----------|-----------|
| 输出细化 | 当前答案/产物 | 低 | 自动 |
| 记忆学习 | 经验记录/检索索引 | 低-中 | 自动 |
| 技能学习 | 程序/脚本/工具策略 | 中 | 证据门控 |
| 策略学习 | Prompt/路由/规划策略 | 中-高 | 人工审核 |
| 权重学习 | 适配器/模型参数 | 高 | 人工审核 |
| 元改进 | 改进机制本身 | 高-极高 | 人工+多重验证 |

**适用场景**:
- 需要高安全保证的系统
- 长期运行的个人助手
- 递归自改进研究

**实施要点**:

### 模式28: 螺旋升层自进化 (Spiral Meta-Upgrade)

**核心思想**: 通过螺旋递归升层避免平面循环震荡，实现真正的元认知超越

**研究来源**: 螺旋数学理论 (张智明, 2024-2025) + DGM/HyperAgents实践 (2026)

**核心概念**:
- **平面迭代** (Iteration): Sₙ = F(Sₙ₋₁) —— 在同一维度循环
- **螺旋超越** (Transcendence): Sₙ = Φ(Sₙ₋₁, d) —— 引入新维度d

**螺旋升层算子 Φ**:
```
Level 0: 对象层 - 修改任务策略
Level 1: 元层 - 修改"如何修改策略"（反思方法）
Level 2: 元-元层 - 修改"如何反思"（认知框架）
Level N: 每升一层，改变"看问题的方式"
```

**实现框架**:
```python
def spiral_self_improving_agent(task, init_policy, max_level=3):
    policy = init_policy
    archive = []
    
    for level in range(max_level):
        best = policy
        for cycle in range(cycles_per_level):
            result = execute(policy, task)
            score = evaluate(result, task)
            
            # 同层迭代：分析失败，修改策略
            if score < target:
                candidate = mutate_policy(policy, diagnose(result))
                if evaluate(execute(candidate, task), task) > score:
                    best = candidate
        
        archive.append(best)
        
        # ★ 螺旋超越：扩展工具集、加深critique、改写meta-rule
        policy = elevate_meta(
            best,
            level=level,
            extra_tools=expand_toolset(level),
            metacritique_depth=level + 1
        )
        
        # 沙箱验证
        assert sandbox_verify(policy), "Self-modification failed safety gate"
    
    return archive[-1]
```

**Prompt设计**:
```
你是一个具有螺旋元认知的Coding Agent。
Round 1：直接解题。
Round 2：批判Round 1的推理链，指出隐含假设。
Round 3：批判你做Round 2批判的方式本身（二阶反思）。
若无新视角产生，停止升层输出当前最佳答案。
```

**工程Checklist**:
- [ ] 分离对象层/元层/元-元层代码
- [ ] 元层代码可编辑（DGM思路）
- [ ] 给每轮输出打螺旋层级标签（用于RLHF/DPO标注）
- [ ] 沙箱+差分测试必做

**适用场景**:
- 复杂推理任务
- 需要突破性创新的场景
- 追求AGI的研究项目

**注意事项**:
- 高计算成本（每层嵌套循环）
- 需要强大的基础模型支撑
- 可能产生难以预测的元级变更
