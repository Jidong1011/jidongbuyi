# 进化模式参考库

> 收录各类AI Agent自循环迭代的最佳实践模式

---

## 模式目录

### 1. 定时扫描型 (Scheduled Scanning)

**适用场景**：
- 知识密集型Skill（研究、学习类）
- 领域快速变化（AI技术、市场趋势）
- 需要持续跟踪外部进展

**核心机制**：
```
Cron定时触发 → 多源搜索 → 差异分析 → 知识更新
```

**成功案例**：
- deep-dive skill：每3天扫描同类研究工具
- news-tracker：每日扫描行业新闻

**配置模板**：
```yaml
triggers:
  cron:
    enabled: true
    interval: "0 0 */3 * *"  # 每3天

perception:
  search_keywords:
    - "[domain] best practice"
    - "[domain] new method"
  sources:
    - arxiv
    - github
    - tech_blogs
```

### 2. 反馈驱动型 (Feedback-Driven)

**适用场景**：
- 交互密集型Agent（客服、助手）
- 需要持续优化用户体验
- 用户反馈容易获取

**核心机制**：
```
用户交互 → 收集反馈 → 失败分析 → Prompt优化
```

**成功案例**：
- Claude的RLHF训练
- 客服Agent的回复优化

**配置模板**：
```yaml
triggers:
  feedback:
    enabled: true
    threshold: 3  # 连续3次负面反馈触发
  performance:
    enabled: true
    metric: "success_rate"
    threshold: 0.85

perception:
  feedback_channels:
    - explicit_rating  # 显式评分
    - implicit_signal  # 隐式信号（重试、放弃等）
```

---

### 3. 竞争进化型 (Competitive Evolution)

**适用场景**：
- 需要多方案对比（Prompt、工作流）
- 有明确的性能指标
- 可以A/B测试

**核心机制**：
```
多版本并行 → A/B测试 → 优胜劣汰 → 变异生成新版本
```

**成功案例**：
- 广告系统创意优化
- 推荐算法参数调优

**配置模板**：
```yaml
triggers:
  competition:
    enabled: true
    population_size: 5  # 保持5个版本
    selection_rate: 0.2  # 淘汰20%
    mutation_rate: 0.3  # 变异30%

evaluation:
  criteria:
    - metric: "conversion_rate"
      weight: 0.5
    - metric: "user_satisfaction"
      weight: 0.3
    - metric: "efficiency"
      weight: 0.2
```

### 4. 性能触发型 (Performance-Triggered)

**适用场景**：
- SLA要求严格的生产系统
- 性能下降需要快速响应
- 自动故障恢复

**核心机制**：
```
持续监控 → 异常检测 → 自动诊断 → 修复/回滚
```

**配置模板**：
```yaml
triggers:
  monitoring:
    enabled: true
    metrics:
      - name: "success_rate"
        threshold: 0.95
        operator: "<"
      - name: "latency_p99"
        threshold: 2000
        operator: ">"
      - name: "error_rate"
        threshold: 0.05
        operator: ">"

execution:
  auto_remmediate: true  # 自动修复
  escalation: true  # 升级通知
```

## 进化评估框架

### 评估维度

| 维度 | 指标 | 权重 | 评估方法 |
|------|------|------|----------|
| **效果** | 成功率 | 40% | 任务完成统计 |
| **效率** | Token/时间消耗 | 25% | 性能监控 |
| **体验** | 用户满意度 | 25% | 反馈收集 |
| **稳定** | 失败率/异常 | 10% | 错误日志 |

### 进化质量评级

- **S级**：所有指标提升 > 20%，无副作用
- **A级**：核心指标提升 > 10%，无重大副作用
- **B级**：有提升但 < 10%，或有轻微副作用
- **C级**：无明显提升，或有明显副作用 → 回滚

## 常见陷阱与对策

### 陷阱1：过度进化
**症状**：频繁变更导致不稳定
**对策**：
- 设置冷却期（一次进化后至少N天才能下次）
- 建立变更队列，批量处理

### 陷阱2：局部最优
**症状**：在小范围内优化，错过更大改进机会
**对策**：
- 定期进行"探索性"大版本尝试
- 引入随机变异机制

### 陷阱3：用户困惑
**症状**：Agent行为频繁变化，用户难以适应
**对策**：：
- 核心行为保持稳定
- 重大变更提前告知
- 提供版本切换选项

### 陷阱4：进化停滞
**症状**：长期无有效改进
**对策**：
- 引入外部视角（其他Agent评估）
- 定期人工review

## 模式7：对抗训练进化 (Adversarial Training Evolution)

**核心思想**：通过内部竞争机制推动能力边界扩展，无需外部数据即可实现自我增强

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│                  对抗训练进化系统                          │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────┐      生成难题      ┌──────────────┐  │
│  │  课程智能体    │ ────────────────→ │  执行智能体   │  │
│  │  (出题者)     │ ←──────────────── │  (解题者)    │  │
│  └──────────────┘      解题反馈      └──────────────┘  │
│         ↑                                    │         │
│         │         螺旋上升闭环                │         │
│         └────────────────────────────────────┘         │
└─────────────────────────────────────────────────────────┘
```

**适用场景**:
- 需要持续提升任务难度的场景
- 缺乏足够训练数据的领域
- 希望突破现有能力边界的探索性任务
- 数学推理、代码生成等可验证领域

**触发条件**:
- 执行智能体成功率超过阈值
- 课程智能体生成的新任务被成功解决
- 需要引入"不确定性奖励"和"重复惩罚"机制

**配置示例**:
```json
{
  "adversarial_training": {
    "curriculum_agent": {
      "reward_components": {
        "uncertainty_reward": "maximize when solver success rate ~50%",
        "tool_usage_reward": "incentive for tool-assisted solutions",
        "repetition_penalty": "BLEU-based similarity penalty"
      }
    },
    "solver_agent": {
      "multi_round_interaction": true,
      "tools": ["code_interpreter", "search", "calculator"],
      "self_consistency_voting": 10
    },
    "evolution_parameters": {
      "filter_threshold": "25%-75% success rate",
      "adaptive_learning_rate": true,
      "max_iterations": 100
    }
  }
}
```

**工业案例**: Agent 0 (2026)、R-Zero (2025) 在数学推理任务上实现18-24%能力提升

**注意事项**:
- 需要可验证的奖励信号（成功/失败）
- 伪标签准确率可能随迭代衰减，需要监控
- 不适合主观评估任务（如创意写作）

## 模式8：经验蒸馏自进化 (Experience Distillation Evolution)

**核心思想**：将原始执行轨迹提炼为可复用的战略原则，而非简单记忆案例

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│                  经验蒸馏自进化系统                        │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────┐    ┌──────────────┐    ┌──────────┐  │
│  │  在线交互层   │ → │  经验蒸馏层   │ → │ 策略进化层 │  │
│  │  (积累轨迹)   │    │ (提取原则)   │    │ (强化学习) │  │
│  └──────────────┘    └──────────────┘    └──────────┘  │
│         ↑                                      │       │
│         └────────────── 闭环反馈 ←─────────────┘       │
└─────────────────────────────────────────────────────────┘
```

**关键组件**:
1. **在线交互**：执行任务并积累完整轨迹
2. **离线蒸馏**：将轨迹抽象为可复用的战略原则
3. **语义去重**：避免重复原则的累积
4. **动态评分**：基于历史有效性持续评估原则质量
5. **策略强化**：使用提炼的原则作为上下文指导决策

**适用场景**:
- 需要长期记忆和知识积累的系统
- 复杂多跳问答任务
- 需要跨任务泛化能力的场景
- 持续性学习系统

**工业案例**: EvolveR (2025)、SkillOS (2026)

## 模式9：Harness工程自进化 (Agentic Harness Engineering)

**核心思想**：不仅进化智能体本身，还进化其周围的工程架构（系统提示、工具、中间件、记忆）

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│                  Harness工程进化系统                       │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐   │
│  │                   Harness 组件                   │   │
│  │  ┌──────────┐ ┌──────────┐ ┌──────────┐        │   │
│  │  │System    │ │ Tool     │ │Middleware│ ...    │   │
│  │  │Prompt    │ │Descriptions│ │  Layer   │        │   │
│  │  └──────────┘ └──────────┘ └──────────┘        │   │
│  └─────────────────────────────────────────────────┘   │
│                         ↓                              │
│  ┌─────────────────────────────────────────────────┐   │
│  │              进化 Agent (元智能体)                │   │
│  │  • 组件可观测性    • 经验可观测性    • 决策可观测性 │   │
│  └─────────────────────────────────────────────────┘   │
│                         ↓                              │
│  ┌─────────────────────────────────────────────────┐   │
│  │              评估与验证管道                      │   │
│  │  • A/B测试  • 回滚机制  • 预测验证                │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**三大可观测性支柱**:
1. **组件可观测性**：Harness解耦为7种正交组件类型
2. **经验可观测性**：分层蒸馏轨迹证据（Per-task + Benchmark-level）
3. **决策可观测性**：自声明预测 + 可控编辑

**工业案例**: AHE (复旦&北大, 2026) - Terminal-Bench 2上69.7%→77.0%

## 模式10：多智能体协同进化 (Multi-Agent Co-Evolution)

**核心思想**：多个专业智能体在共享持久内存中异步探索、反思和协作，实现开放式发现

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│              多智能体协同进化系统 (CORAL风格)              │
├─────────────────────────────────────────────────────────┤
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐    │
│  │ Agent A │  │ Agent B │  │ Agent C │  │ Agent D │    │
│  │ (探索者) │  │ (验证者) │  │ (综合者) │  │ (创新者) │    │
│  └────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘    │
│       └─────────────┴─────────────┴─────────────┘       │
│                         ↓                               │
│              ┌─────────────────────┐                    │
│              │   共享持久内存池     │                    │
│              │  • 发现的知识        │                    │
│              │  • 失败的教训        │                    │
│              │  • 成功的模式        │                    │
│              └─────────────────────┘                    │
│                         ↓                               │
│              ┌─────────────────────┐                    │
│              │  心跳干预机制        │                    │
│              │  (健康检查/资源管理)  │                    │
│              └─────────────────────┘                    │
└─────────────────────────────────────────────────────────┘
```

**关键机制**:
1. **异步执行**：各Agent独立运行，不阻塞彼此
2. **共享内存**：所有发现的知识实时同步到共享池
3. **心跳干预**：定期检查Agent健康状态，防止资源耗尽
4. **知识重用**：Agent可以查询并利用其他Agent的发现

**适用场景**:
- 开放式科学发现
- 复杂系统优化
- 需要多角度探索的创意任务
- 大规模搜索空间问题

**触发条件**:
- 单Agent长期无法突破
- 问题空间需要多样化探索策略
- 需要验证和交叉确认的发现

**配置示例**:
```yaml
co_evolution:
  agent_pool:
    - role: explorer
      strategy: random_walk
      count: 2
    - role: validator
      strategy: verification_first
      count: 1
    - role: synthesizer
      strategy: pattern_recognition
      count: 1
  shared_memory:
    type: persistent_vector_db
    sync_interval: 30s
  heartbeat:
    interval: 60s
    max_idle_time: 300s
    resource_limit:
      cpu: 80%
      memory: 4GB
```

**工业案例**: CORAL (2026) - 在Anthropic内核工程任务上将最佳成绩从1363提升到1103周期

**注意事项**:
- 需要仔细的并发控制
- 共享内存需要版本控制防止冲突
- 心跳机制防止"僵尸Agent"

## 模式11：元认知自我修改 (Metacognitive Self-Modification)

**核心思想**：不仅改进任务解决行为，还改进生成改进的机制本身 - 进化过程的进化

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│              元认知自我修改系统 (HyperAgents风格)          │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐   │
│  │              统一可编辑程序                        │   │
│  │  ┌─────────────────┐  ┌─────────────────────┐  │   │
│  │  │   Task Agent    │  │     Meta Agent      │  │   │
│  │  │  (解决目标任务)  │  │ (修改Task Agent和   │  │   │
│  │  │                 │  │   自身修改过程)     │  │   │
│  │  └─────────────────┘  └─────────────────────┘  │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │           Meta-Level Modification               │   │
│  │  • 进化策略本身的改进                             │   │
│  │  • 评估指标的调整                                │   │
│  │  • 选择压力的设计                                │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │         自我加速改进循环                          │   │
│  │  改进速度本身可以被改进 → 超线性增长              │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**关键突破**:
1. **自指代架构**：Task Agent 和 Meta Agent 整合为单一可编辑程序
2. **元级可编辑**：修改机制本身也是可编辑的
3. **跨域迁移**：元级改进可以跨任务领域复用
4. **累积效应**：改进会加速改进的速度

**适用场景**:
- 需要长期持续改进的核心系统
- 跨多个任务领域的通用进化框架
- 追求超线性改进速度的场景

**触发条件**:
- 传统进化模式达到平台期
- 需要突破"局部最优"陷阱
- 追求通用智能的终极形态

**实现要点**:
```yaml
metacognitive:
  self_reference:
    unified_program: true  # Task和Meta整合
    editable_meta: true    # 元过程可编辑
  evolution_of_evolution:
    strategy_pool:
      - mutation_operators
      - selection_pressure
      - evaluation_metrics
    improvement_targets:
      - task_performance
      - evolution_speed
      - generalization
  cross_domain_transfer:
    meta_improvements_persist: true
    domain_agnostic_principles: true
```

**工业案例**: Meta HyperAgents (2026) - 跨四个领域实现自我加速改进，元级改进跨域迁移

**安全考量**:
- 需要强沙箱隔离
- 人工审核所有元级变更
- 设置改进速度上限防止失控

## 模式12：可审计技能图进化 (Auditable Skill-Graph Evolution)

**核心思想**：将自我改进视为向可审计技能图的迭代编译，每个改进都是可验证、可复用的显式技能

**架构**:
```
┌─────────────────────────────────────────────────────────┐
│              可审计技能图进化系统 (ASG-SI风格)             │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────┐    ┌──────────────┐    ┌──────────┐  │
│  │  成功轨迹     │ → │   技能提取    │ → │ 技能验证  │  │
│  │  (带上下文)   │    │ (标准化接口)  │    │ (重放验证) │  │
│  └──────────────┘    └──────────────┘    └────┬─────┘  │
│                                                ↓       │
│  ┌─────────────────────────────────────────────────┐   │
│  │              可审计技能图                         │   │
│  │  ┌─────────┐  ┌─────────┐  ┌─────────┐          │   │
│  │  │ Skill 1 │──│ Skill 2 │──│ Skill 3 │  ...     │   │
│  │  │[verified]│  │[verified]│  │[verified]│         │   │
│  │  └─────────┘  └─────────┘  └─────────┘          │   │
│  │                                                 │   │
│  │  属性：显式接口、可验证性、可组合性、可追溯性       │   │
│  └─────────────────────────────────────────────────┘   │
│                                                ↓       │
│  ┌─────────────────────────────────────────────────┐   │
│  │              审计日志与治理                       │   │
│  │  • 每个技能的来源证据                            │   │
│  │  • 验证通过的检查点                              │   │
│  │  • 学习信号的解构                                │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**关键组件**:
1. **技能提取**：从成功轨迹中标准化提取技能
2. **显式接口**：每个技能有明确的输入输出契约
3. **Verifier-backed验证**：通过重放验证技能有效性
4. **审计日志**：完整记录技能来源、验证过程和升级历史

### 模式22: 三层协同进化 (Three-Layer Co-Evolution, APEX)

**核心思想**: 同时进化三个正交维度——Harness修补、行为原则蒸馏、工作流拓扑进化

**研究来源**: APEX (Grace AI Technology, 2026-06, arXiv:2606.15363)

**三层架构**:
```
┌─────────────────────────────────────────────────────────┐
│              三层协同进化系统 (APEX风格)                   │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────────────────────────────────────┐   │
│  │  Layer 1: Harness Review (失败模式修补)          │   │
│  │  • 从失败轨迹提取系统性故障模式                   │   │
│  │  • 生成针对性规则补丁                            │   │
│  │  • 注入系统提示作为显式规则                       │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │  Layer 2: Principle Distillation (原则蒸馏)      │   │
│  │  • 从成功轨迹提取高质量行为模式                   │   │
│  │  • 蒸馏为可复用的行为原则                        │   │
│  │  • 在线应用于推理阶段                            │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │  Layer 3: Workflow Topology (拓扑进化)           │   │
│  │  • 基于结构健康度评估工作流DAG                   │   │
│  │  • 蒙特卡洛树搜索最优拓扑                        │   │
│  │  • 选择结构健康度最高的工作流                     │   │
│  └─────────────────────────────────────────────────┘   │
│                          ↓                             │
│  ┌─────────────────────────────────────────────────┐   │
│  │         APEX Health Score (综合健康评分)         │   │
│  │  H = f(覆盖率, 原则丰富度, 结构质量)              │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**关键创新**:
1. **正交进化轴**: 三个维度解决不同的失败模式，互不替代
2. **共享轨迹池**: 所有层从同一生产轨迹池提取证据
3. **复合健康评分**: APEX Health Score量化多维度进化进展
4. **无合成基准**: 完全基于真实生产轨迹，无需人工设计测试集

**APEX Health Score公式**:
```
H = w₁ × Coverage + w₂ × PrincipleRichness + w₃ × StructuralQuality

其中:
- Coverage: Harness补丁对失败模式的覆盖率
- PrincipleRichness: 蒸馏原则的数量和质量
- StructuralQuality: 工作流拓扑的结构健康度
```

**效果数据**:
- Joe Agent + 114真实任务轨迹 + 18天跨度 + 15节点计算集群
- APEX Health Score: 0.300 → 0.570 (+90%)
- 蒸馏6个新颖可复用原则
- 选出研究优先工作流拓扑 (结构评分0.900, +20%)
- 成本: 仅4 LLM调用 (~270s) 本地qwen2.5-coder:32b

**适用场景**: 
- 生产级Agent持续优化
- 需要多维度改进的复杂系统
- 真实部署环境（无合成基准）

**实施建议**:
```yaml
apex_evolution:
  shared_trace_pool: "production_traces.db"
  layers:
    l1_harness:
      failure_keywords: ["error", "fail", "wrong", "mistake"]
      top_n_traces: 30
      patches_per_run: 3
    l2_principles:
      quality_score_weights:
        lesson_length: 0.4
        action_count: 0.3
        files_changed: 0.2
        external_source: 0.1
      principles_per_run: 6
    l3_topology:
      search_algorithm: "mcts"
      fitness_metrics:
        - structural_complexity
        - error_handling_coverage
        - parallelization_opportunities
  health_score:
    weights: [0.4, 0.3, 0.3]  # L1, L2, L3
```

### 模式25: 自我归因轨迹优化 (Self-Attributing Trajectory Optimization)

**三模块架构**:
```
┌─────────────────────────────────────────────────────────┐
│              自我归因轨迹优化系统 (AgentEvolver风格)        │
├─────────────────────────────────────────────────────────┤
│  ┌──────────────┐    ┌──────────────┐    ┌──────────┐  │
│  │ 自我提问      │ → │ 自我导航      │ → │ 自我归因  │  │
│  │(任务生成)     │    │(经验检索)     │    │(信用分配) │  │
│  └──────────────┘    └──────────────┘    └────┬─────┘  │
│                                               ↓       │
│  ┌─────────────────────────────────────────────────┐   │
│  │              闭环训练                            │   │
│  │  Master节点统一调度 + 服务化解耦 + 上下文管理器   │   │
│  └─────────────────────────────────────────────────┘   │
```

**三个核心机制**:

1. **自我提问 (Self-Questioning)**:
   - 利用LLM生成能力主动合成候选任务
   - 打破冷启动困境
   - 自动生成多样化训练课程

2. **自我导航 (Self-Navigating)**:
   - 将历史成功/失败抽象为结构化文本经验
   - 检索相似过往经验指导当前决策
   - "举一反三"能力

3. **自我归因 (Self-Attributing)**:
   - 基于LLM的过程奖励模型
   - 对轨迹中每个动作步骤细粒度因果分析
   - 将结果奖励转化为过程监督信号

**效果数据** (14B模型):
- AppWorld/BFCL: 29.8% → 57.6% (近乎翻倍)

- 训练步数减少: 55.6% (AppWorld), 66.7% (BFCL)
- 跨域泛化: AppWorld训练模型用于BFCL，性能衰减极小

**适用场景**: 
- 长程复杂任务
- 奖励稀疏环境
- 需要快速收敛的训练

| **源代码重写** | MOSS | 生产失败驱动的结构修复 | 生产环境 |
| **混合工作流** | HyEvo | 概率+确定性节点自动组合 | 成本敏感场景 |
| **元认知进化** | HyperAgents | 修改进化机制本身 | 跨域通用 |

### 设计原则更新

1. **证据锚定**：所有进化必须基于具体的失败证据或性能数据，而非猜测
2. **渐进验证**：每个候选变更必须经过沙盒验证才能进入生产
3. **异步协作**：多Agent场景使用异步执行+共享内存，避免阻塞
4. **异构混合**：合理利用LLM和代码的不同优势，自动优化组合
5. **元级可编辑**：考虑进化过程本身的可进化性

### 安全与治理新要求

- **可审计性**：每个进化步骤必须有完整的审计日志
- **人工门控**：关键变更需人工确认
- **自动回滚**：健康检查失败时自动回滚
- **沙箱隔离**：所有候选变更在隔离环境中验证

## 🆕 2026年6月新增模式（Evo Skill自循环进化扫描结果）

> 以下模式基于2026年6月最新研究扫描（arXiv 2026-02至2026-06）

---

### 模式16: 能力保持型进化 (Capability-Preserving Evolution, CPE)

**核心思想**: 在自我进化过程中防止"遗忘"——新能力提升不以牺牲已有能力为代价

**研究来源**: "Do Self-Evolving Agents Forget?" (2026-05)

**实现要点**:
- 建立能力基线测试套件（Capability Baseline Suite）
- 每次进化前运行回归测试（Regression Testing）
- 多目标优化：提升目标能力 + 保持已有能力
- 帕累托前沿求解（Pareto Frontier Optimization）

**关键指标**:
```
能力保持率 = 进化后旧任务通过率 / 进化前旧任务通过率
净能力增益 = Σ(新任务提升) - Σ(旧任务退化)
```

**适用场景**: 长期运行的生产级Agent、关键业务系统

---

### 模式17: Harness优化进化 (Harness-Optimizing Evolution)

**核心思想**: 固定LLM参数，通过优化运行框架（Harness）实现能力提升

**研究来源**: Self-Harness (上海AI Lab, 2026-06, arXiv:2606.09498)

**三阶段循环**:
1. **Weakness Mining（弱点挖掘）**: 从执行轨迹分析失败模式
2. **Harness Proposal（框架提案）**: 生成针对性的Harness改进方案
3. **Proposal Validation（提案验证）**: 回归测试确保无退化

**四类改进类型**:
- 系统提示词修改（System Prompt Modification）
- 工具包装器添加（Tool Wrapper Enhancement）
- 验证步骤注入（Verification Step Injection）
- 规划模板更新（Planning Template Update）

**关键发现**: 
- Harness-Updating（生成更新）vs Harness-Benefit（从更新受益）能力分离
- 弱模型也能生成高质量更新，中等能力模型受益最大（倒U型曲线）

**适用场景**: 无法/不愿微调模型的场景、多模型统一优化

---

### 模式18: 回顾性工具包优化 (Retrospective Harness Optimization, RHO)

**核心思想**: 无需外部标准答案，通过自我反思改进工具包

**研究来源**: 港城大×微软 (2026-06, arXiv:2606.05922)

**三步进化**:
1. **诊断（Diagnosis）**: 用DPP筛选核心学习案例（难度70% + 多样性30%）
2. **重试（Retry）**: 自我验证 + 自我一致性检查
3. **改造（Refinement）**: 生成三套方案，内部评分选出最优

**效果数据**:
- SWE-BenchPro: 59% → 78% (+19%)
- 优于依赖标准答案的meta-Harness方法（62%）

**适用场景**: 无标准测试集的真实部署环境

---

### 模式19: 可执行子Agent积累 (Executable Subagent Accumulation)

**核心思想**: 将成功经验保存为可执行代码（而非文本描述），形成可复用的子Agent库

**研究来源**: AgentFactory (北大, 2026-03, arXiv:2603.18000)

**三阶段生命周期**:
1. **Install**: 从零构建子Agent解决初始问题
2. **Self-Evolve**: 检测子Agent局限并自主改进
3. **Deploy**: 导出成熟子Agent为独立Python模块

**核心优势**:
- 子Agent是纯Python代码，可跨平台移植
- 持续基于执行反馈优化
- 解决"文本经验无法保证可靠重执行"问题

**适用场景**: 复杂工作流自动化、企业级Agent系统

---

### 模式20: 步骤级技能适应 (Step-Level Skill Adaptation)

**核心思想**: 细粒度失败归因，精准更新技能

**研究来源**: SkillAdaptor (阿里, 2026-06, arXiv:2606.01311)

**实现流程**:
1. 识别第一个可操作的故障步骤
2. 将责任关联到候选技能
3. 在显式接受检查下应用针对性更新

**效果数据**:
- PinchBench: +1.5 points
- Claw-Eval: +1.8 points  
- WebShop: +1.7 points (成功率)

**特点**: 训练无关（Training-free），可即插即用到OpenClaw类Harness

**适用场景**: 交互式任务、长周期任务

---

### 模式21: 人机协同进化 (Human-in-the-Loop Co-evolution)

**核心思想**: 人类设定方向，Agent执行进化，关键节点人工审核

**实践来源**: AutoClaw自进化机制 (智谱, 2026-04)

**工作流程**:
1. Agent自动扫描对话/执行过程
2. 识别纠正指令、新方法、用户偏好
3. 以"进化请求"形式弹出，经用户批准后写入长期记忆

**关键原则**:
- 战略方向人类定（Should we pivot?）
- 质量标准人类设（What counts as good?）
- 伦理边界人类划（What's allowed?）
- 进化执行Agent做（How to improve?）

**适用场景**: 需要平衡自主性与可控性的场景
